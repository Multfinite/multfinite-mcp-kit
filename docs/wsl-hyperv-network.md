# Сеть Hyper-V, WSL 2 и Windows-ВМ с выходом в интернет

Это отдельная, необязательная настройка сети для [Multfinite MCP Kit](../README.md). В примере Windows-хост, Windows-VM и, **только при поддержке выбранной конфигурацией WSL**, WSL 2 используют внутреннюю подсеть. Команды изменяют сеть компьютера и могут прервать удалённое подключение. Выполняйте их только на своей машине, имея локальный доступ и возможность отката. Нативная настройка Windows, Hyper-V и WSL по этому руководству не проверялась.

## Схема и важное ограничение WSL

| Участник | Пример адреса | Назначение |
| --- | --- | --- |
| Внутренний коммутатор Hyper-V | `NATSwitch` | Соединяет хост и подключённые к нему виртуальные адаптеры. |
| Подсеть | `192.168.100.0/24` | Маска `255.255.255.0`; адреса ниже должны быть свободны. |
| Windows-хост | `192.168.100.1` | Адрес его `vEthernet (NATSwitch)` и шлюз для гостей; в WSL можно задать ему имя `wslhost`. |
| Windows-VM | `192.168.100.Y`, Y=11 | Статический адрес с шлюзом `192.168.100.1`. |
| WSL 2 | `192.168.100.X`, X=10 | Только **условный устаревший вариант** с подключением WSL к `NATSwitch`; не гарантируется. |

Windows выполняет исходящий NAT для `192.168.100.0/24` через своё обычное подключение к интернету. Внутренний коммутатор сам по себе не соединяет гостей напрямую с физической LAN и не открывает входящие соединения из неё. WinNAT **не выдаёт адреса по DHCP и не является DNS-сервером**: адрес, шлюз и работающий DNS задаются внутри каждого гостя. Изоляция коммутатора и NAT не шифруют трафик.

**Не рассчитывайте, что WSL обязательно получит `192.168.100.10` или подключится к этому коммутатору.** Microsoft пометила режим `networkingMode=bridged` устаревшим начиная с WSL 2.4.5; текущий [справочник WSL](https://learn.microsoft.com/en-us/windows/wsl/wsl-config) больше не перечисляет прежние параметры `vmSwitch` и `dhcp`. В [обсуждении WSL](https://github.com/microsoft/WSL/issues/9251) сообщается, что даже в некоторых версиях с `bridged` внутренний коммутатор не работает. Режим `networkingMode` документирован для Windows 11 22H2 и новее. Поведение зависит от конкретных версий Windows и WSL; не понижайте версию ради этого примера.

- **Обычный вариант для WSL:** оставьте NAT WSL по умолчанию или рассмотрите рекомендуемый Microsoft `mirrored` на Windows 11 22H2+ по [документации по сети WSL](https://learn.microsoft.com/en-us/windows/wsl/networking). В `mirrored` хост и WSL могут обращаться друг к другу через IPv4 `127.0.0.1`; это не подключение WSL к `NATSwitch` и не гарантия отдельного адреса `.10`. В обычном NAT адреса WSL могут меняться. Имя `wslhost` на `.1` имеет смысл только после проверки маршрута именно до этого интерфейса хоста.
- **Если необходимы именно одна подсеть и постоянный адрес `.10`:** используйте обычную Linux-ВМ Hyper-V на `NATSwitch` со статическими настройками либо отдельно спроектированную поддерживаемую сеть. Раздел про устаревший WSL ниже пригоден лишь для эксперимента на версии, в которой такое подключение уже подтверждено; при ошибке возвращайтесь к сохранённой конфигурации. Настройка Windows-ВМ через Hyper-V ниже не зависит от `bridged` WSL.

## 1. Подготовка и проверка Windows-хоста

Нужны включённая виртуализация процессора, WSL 2 и доступный Hyper-V с инструментами управления. Hyper-V для обычных ВМ требует поддерживаемой редакции Windows, например Pro, Enterprise или Education; в Windows Home полный Hyper-V недоступен. Для Windows Server установку роли выполняют иначе. При отсутствии компонента следуйте инструкциям Microsoft по [установке Hyper-V](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/install-hyper-v) и [установке WSL](https://learn.microsoft.com/en-us/windows/wsl/install); возможна перезагрузка. Не заменяйте и не удаляйте существующие Docker/WSL-сети при установке комплекта.

На **хосте**, в PowerShell от администратора, сначала только посмотрите состояние:

```powershell
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsVersion
wsl --version
wsl --status
wsl --list --verbose
Get-VMSwitch | Format-Table Name, SwitchType
Get-NetNat | Format-Table Name, InternalIPInterfaceAddressPrefix
Get-NetAdapter | Format-Table Name, InterfaceDescription, ifIndex, Status, MacAddress
Get-NetIPAddress -AddressFamily IPv4 | Sort-Object InterfaceIndex | Format-Table IPAddress, PrefixLength, InterfaceAlias
Get-NetRoute -AddressFamily IPv4 | Sort-Object DestinationPrefix | Format-Table DestinationPrefix, NextHop, InterfaceAlias, RouteMetric
Get-DnsClientServerAddress -AddressFamily IPv4 | Format-Table InterfaceAlias, ServerAddresses
```

Если `wsl --version` не распознаётся, WSL может быть старой встроенной версией: проверьте возможность обновления по документации Microsoft. Убедитесь, что нужный дистрибутив работает именно в WSL 2. До изменений запишите текущие переключатели ВМ, адреса, DNS и маршруты, в том числе VPN; в гостевой ВМ отдельно сохраните её сетевую конфигурацию. Не выполняйте команды создания повторно при частичном успехе: сначала проверьте фактическое состояние.

**Подсеть — лишь пример.** Проверьте, что `192.168.100.0/24` не пересекается с физической сетью, VPN, WSL, сетями Docker и другими маршрутами, кроме обычного маршрута по умолчанию `0.0.0.0/0`. Убедитесь по учёту адресов и настройкам всех гостей, что `.1`, `.10` и `.20` свободны и не выдаются другим DHCP-сервером; отсутствие ответа на ping этого не доказывает. При конфликте выберите другую свободную подсеть и согласованно замените **все** адреса, маршруты и правила в примере, включая регулярное выражение `192[.]168[.]100[.]10` в скрипте WSL.

Microsoft предупреждает, что WinNAT поддерживает один внутренний NAT-префикс на хост; Docker, контейнеры или другие программы уже могут им пользоваться. Если `Get-NetNat` показывает существующий NAT либо уже есть `NATSwitch`, адрес или маршрут из примера, остановитесь и сначала разберитесь с их назначением и поддерживаемой совместной конфигурацией. Не удаляйте чужой NAT, коммутатор или Docker-сети и не создавайте второй NAT вслепую. Даже пустой вывод `Get-NetNat` не заменяет проверки HNS/Docker и маршрутов.

Для дополнительного просмотра на хосте можно выполнить следующие **команды только чтения**, если соответствующие средства доступны. Вывод может содержать сведения о внутренних сетях:

```powershell
if (Get-Command Get-HnsNetwork -ErrorAction SilentlyContinue) {
    Get-HnsNetwork | ConvertTo-Json -Depth 8
} else {
    Write-Host 'Get-HnsNetwork недоступна; проверьте HNS другими средствами.'
}
if (Get-Command docker -ErrorAction SilentlyContinue) {
    docker context show
    docker network ls
}
```

В подходящем Docker-контексте проверьте подсети нужных сетей через `docker network inspect`, указав их реальные имена; при недоступном демоне выполните эту проверку после его запуска. В работающем дистрибутиве WSL проверьте `ip -4 address` и `ip -4 route`. Просмотрите также корпоративные/VPN-маршруты: список Docker-сетей сам по себе не выявляет все пересечения.

Перед экспериментом с WSL сохраните `%UserProfile%\.wslconfig`, если он есть, например отдельной копией с новым именем. Этот файл действует на **все** дистрибутивы WSL 2 текущего пользователя:

```powershell
$wslConfig = Join-Path $env:USERPROFILE '.wslconfig'
$backup = "$wslConfig.mcpkit-backup-$(Get-Date -Format 'yyyyMMdd-HHmmss')"
if (Test-Path -LiteralPath $wslConfig) {
    if (Test-Path -LiteralPath $backup) { throw 'Имя резервной копии уже занято; выберите другое.' }
    Copy-Item -LiteralPath $wslConfig -Destination $backup -ErrorAction Stop
    Write-Host "Копия: $backup"
} else {
    Write-Host 'Файла .wslconfig не было; запомните это для отката.'
}
```

В нужном дистрибутиве WSL сохраните `/etc/wsl.conf`, `/etc/hosts` и `/etc/resolv.conf`, включая символические ссылки, а также текущее содержимое DNS. Следующая команда создаёт новый приватный каталог резервной копии и не заменяет исходные файлы. При ошибке копирования она прекращает работу; проверьте созданную копию до дальнейших изменений:

```sh
(
  set -eu
  backup_dir="$(mktemp -d "$HOME/mcpkit-network-backup.XXXXXX")"
  chmod 700 "$backup_dir"
  for file in /etc/wsl.conf /etc/hosts /etc/resolv.conf; do
    if [ -e "$file" ] || [ -L "$file" ]; then
      sudo cp -a -- "$file" "$backup_dir/"
    else
      printf '%s отсутствовал\n' "$file"
    fi
  done
  if sudo test -r /etc/resolv.conf; then
    sudo cp -L -- /etc/resolv.conf "$backup_dir/resolv.conf.content"
  else
    printf 'Содержимое DNS-файла недоступно; проверьте вручную.\n' >&2
  fi
  printf 'Резервная копия: %s\n' "$backup_dir"
)
```

Запишите, каких файлов изначально не было. Если `resolv.conf` — ссылка на временный файл, одной копии ссылки недостаточно: приведённая команда отдельно сохраняет её содержимое; выясните также, какая служба управляет DNS. Резервные копии могут содержать внутренние адреса и имена, храните их приватно.

## 2. Внутренний коммутатор и WinNAT

Продолжайте в PowerShell **хоста от администратора**, только если проверка выше не обнаружила конфликтов и существующих зависимостей. Создайте внутренний коммутатор:

```powershell
New-VMSwitch -Name 'NATSwitch' -SwitchType Internal
Get-VMSwitch -Name 'NATSwitch' | Format-List Name, SwitchType
Get-NetAdapter | Format-Table Name, InterfaceDescription, ifIndex, Status
```

Найдите созданный для этого коммутатора адаптер управления хоста. Обычно он называется `vEthernet (NATSwitch)`; имя и индекс проверьте в выводе. Если имя отличается, замените строку выбора на **точное проверенное имя**. Не выбирайте первый адаптер из списка и не применяйте адрес к физическому Ethernet/Wi-Fi или чужому виртуальному адаптеру.

```powershell
$adapter = Get-NetAdapter -Name 'vEthernet (NATSwitch)' -ErrorAction Stop
$adapter | Format-List Name, InterfaceDescription, ifIndex, MacAddress
Get-NetIPAddress -InterfaceIndex $adapter.ifIndex -AddressFamily IPv4
```

Только убедившись, что это новый нужный адаптер и адрес на нём ещё не задан, добавьте адрес хоста:

```powershell
New-NetIPAddress -InterfaceIndex $adapter.ifIndex -IPAddress '192.168.100.1' -PrefixLength 24 -ErrorAction Stop
Get-NetIPAddress -InterfaceIndex $adapter.ifIndex -AddressFamily IPv4 | Format-Table IPAddress, PrefixLength, AddressState
```

Прежде чем продолжить, убедитесь, что `.1/24` назначен нужному адаптеру и проверка уникальности адреса завершилась: `AddressState` должен стать `Preferred`. Если он ещё `Tentative`, повторите просмотр позже; при ошибке или состоянии `Duplicate` остановитесь. После успешной проверки создайте NAT:

```powershell
New-NetNat -Name 'MCPKit-NAT' -InternalIPInterfaceAddressPrefix '192.168.100.0/24' -ErrorAction Stop
Get-NetNat -Name 'MCPKit-NAT' | Format-List Name, InternalIPInterfaceAddressPrefix
```

**Не задавайте шлюз по умолчанию на `vEthernet (NATSwitch)` хоста**: выход хоста в интернет остаётся через его обычный физический или VPN-интерфейс. Если создание одной из команд не удалось, не удаляйте остальные сети для повтора; проверьте созданные объекты и раздел отката. Подробности и ограничение WinNAT приведены в [руководстве Microsoft](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/setup-nat-network).

## 3. WSL: выбор режима и статический адрес

### Поддерживаемые режимы без адреса `.10`

Для большинства установок достаточно оставить существующую сеть WSL по умолчанию. При необходимости Microsoft рекомендует `mirrored` на Windows 11 22H2+: в уже существующем `%UserProfile%\.wslconfig` можно изменить или добавить **только** ключ `networkingMode` в существующей секции `[wsl2]`, сохранив остальные ключи. Если файла или секции нет, создайте их; не создавайте вторую секцию с тем же именем:

```ini
[wsl2]
networkingMode=mirrored
```

Это пример содержимого секции, **не команда перезаписи всего файла**. Изменение режима влияет на все WSL 2-дистрибутивы, Docker Desktop и доступ к сети; `mirrored` может не подойти конкретному VPN или политике безопасности. Для применения сохраните работу во всех дистрибутивах и Docker, выполните на хосте `wsl --shutdown`, затем запустите нужный дистрибутив и проверьте подключение. Команда останавливает **все** WSL-дистрибутивы. При проблемах верните прежние настройки. Для сети WSL в NAT или `mirrored` не выполняйте команды статического адреса из следующего раздела.

### Устаревший эксперимент: WSL на `NATSwitch`

Переходите к этому разделу только если вы намеренно используете старую схему и **проверили для своей версии**, что WSL умеет подключаться именно к внутреннему `NATSwitch`. Возможный прежний вариант секции выглядел так:

```ini
[wsl2]
networkingMode=bridged
vmSwitch=NATSwitch
dhcp=false
```

Это не поддерживаемое универсальное решение: параметры `vmSwitch` и `dhcp` отсутствуют в текущем справочнике Microsoft, могут игнорироваться или привести к ошибке запуска; для внутреннего коммутатора известны отказы. Не смешивайте этот пример с `mirrored`. При редактировании сохраните другие настройки, не создавайте повторные `[wsl2]` или ключи и заранее сделайте копию. После `wsl --shutdown` запустите нужный дистрибутив и проверьте сообщения WSL. При ошибке, отсутствии интерфейса или невозможности подтвердить подключение к `NATSwitch` **остановитесь и откатите изменения**, а не назначайте адрес случайному интерфейсу.

На Linux в выбранном дистрибутиве изучите интерфейсы и маршруты:

```sh
ip -br link
ip -br -4 address
ip -4 route
ip rule show
```

Вручную определите интерфейс WSL, подключённый именно к `NATSwitch`; это может быть `eth0`, но имя не гарантируется. Не выбирайте `docker0`, `veth` или другой адаптер наугад. Для выбранного интерфейса проверьте состояние и MAC-адрес, заменив пример на фактическое имя:

```sh
nic='eth0'
ip -d link show dev "$nic"
cat "/sys/class/net/$nic/address"
```

При сложной политической маршрутизации, уже существующем IPv4 на этом интерфейсе, другом маршруте по умолчанию или работе сетевого менеджера сначала согласуйте настройку с ним. Ниже показан только чистый отдельный интерфейс без другого маршрута по умолчанию; конфликтующие маршруты и адреса автоматически не удаляются. Убедитесь, что `.10` свободен, и запишите исходное состояние интерфейса. Затем для **разовой проверки**, в той же оболочке и с проверенным `nic`:

```sh
(
  set -eu
  : "${nic:?Сначала укажите проверенный интерфейс}"
  sudo ip link set dev "$nic" up
  sudo ip address add 192.168.100.10/24 dev "$nic"
  sudo ip route add default via 192.168.100.1 dev "$nic"
  ip -4 address show dev "$nic"
  ip -4 route
)
```

Команды не рассчитаны на повторное добавление тех же записей. Блок останавливается при ошибке, но не отменяет уже внесённые изменения. Если адрес или маршрут уже есть, выясните их происхождение; не выполняйте `ip addr flush` и не заменяйте чужой маршрут. Проверьте доступ к хосту и интернету по разделу диагностики. Отсутствие ping само по себе ещё не доказывает ошибку: ICMP может фильтроваться. Только после подтверждения связи приступайте к сохранению настройки. При неудаче удалите лишь добавленные вами адрес и маршрут, как описано в разделе отката, и вернитесь к прежнему режиму WSL.

### Сохранение адреса при запуске дистрибутива

Разовые `ip`-команды не сохраняются после остановки WSL. На Windows 11 или Windows Server 2022 в WSL доступен `[boot] command`: он выполняется от root при запуске **конкретного дистрибутива**, а не при включении Windows без запуска этого дистрибутива. Несколько WSL 2-дистрибутивов обычно используют общий сетевой стек: выберите один ответственный дистрибутив, не запускайте конкурирующую настройку адреса из остальных и учитывайте конфликты портов. При работающем другом сетевом менеджере используйте его согласованный способ или не применяйте этот пример.

Если `/usr/local/sbin/mcpkit-wsl-network` ещё не существует, создайте его от root редактором. Подставьте **проверенные** имя и MAC интерфейса из предыдущего шага; MAC скопируйте точно как показала команда `cat`. Указанные заглушки намеренно не работают:

```sh
#!/bin/sh
set -eu
PATH=/usr/sbin:/usr/bin:/sbin:/bin
nic='ИМЯ_ПРОВЕРЕННОГО_ИНТЕРФЕЙСА'
expected_mac='MAC_ПРОВЕРЕННОГО_ИНТЕРФЕЙСА'

if [ ! -r "/sys/class/net/$nic/address" ] ||
   [ "$(cat "/sys/class/net/$nic/address")" != "$expected_mac" ]; then
  echo 'Интерфейс отсутствует или его MAC изменился; сеть не изменена.' >&2
  exit 1
fi

assigned="$(ip -o -4 address show | awk '$4 ~ /^192[.]168[.]100[.]10\// {print $2 " " $4}')"
if [ -n "$assigned" ] && [ "$assigned" != "$nic 192.168.100.10/24" ]; then
  echo 'Адрес .10 уже назначен иначе; сеть не изменена.' >&2
  exit 1
fi
other_addresses="$(ip -o -4 address show dev "$nic" | awk '$4 != "192.168.100.10/24" {print $4}')"
if [ -n "$other_addresses" ]; then
  echo 'На интерфейсе обнаружен другой IPv4-адрес; сеть не изменена.' >&2
  exit 1
fi
routes="$(ip -4 route show default)"
if [ -n "$routes" ]; then
  printf '%s\n' "$routes" | awk -v nic="$nic" '
    NR == 1 && $1 == "default" && $2 == "via" && $3 == "192.168.100.1" && $4 == "dev" && $5 == nic { ok = 1 }
    END { if (NR != 1 || !ok) exit 1 }
  ' || { echo 'Обнаружен другой маршрут по умолчанию; сеть не изменена.' >&2; exit 1; }
fi

ip link set dev "$nic" up
if [ -z "$assigned" ]; then ip address add 192.168.100.10/24 dev "$nic"; fi
if [ -z "$routes" ]; then ip route add default via 192.168.100.1 dev "$nic"; fi
```

Сделайте новый файл принадлежащим root и исполняемым: `sudo chown root:root /usr/local/sbin/mcpkit-wsl-network` и `sudo chmod 755 /usr/local/sbin/mcpkit-wsl-network`. Запустите его один раз через `sudo /usr/local/sbin/mcpkit-wsl-network`: уже добавленные этим примером адрес и маршрут допускаются, несовпадение MAC, другой IPv4 на интерфейсе или чужой маршрут по умолчанию вызывают ошибку. Скрипт не проверяет занятость адреса на других машинах или все таблицы политической маршрутизации; их нужно проверить заранее. Если WSL меняет MAC или имя интерфейса при перезапуске, скрипт намеренно остановится: снова определите подключение, не отключайте проверку вслепую. При частичной ошибке проверьте реальное состояние перед повтором.

Добавьте строку `command` в существующую секцию `[boot]` файла `/etc/wsl.conf` этого дистрибутива, сохранив остальные параметры. Если секции нет, создайте её:

```ini
[boot]
command=/usr/local/sbin/mcpkit-wsl-network
```

Если `command` уже задан, **не заменяйте его и не создавайте второй ключ**: согласуйте обе команды через собственную проверенную обёртку или используйте сетевой менеджер дистрибутива. На версиях без `[boot] command` нужна отдельная поддерживаемая конфигурация автозапуска. Остановите работу во всех дистрибутивах, выполните на хосте `wsl --shutdown` и откройте выбранный дистрибутив. Проверьте `ip -4 address`, `ip -4 route`, подключение и повторите проверки после перезагрузки хоста. Сам перезапуск WSL не гарантирует поддержку устаревшего коммутатора.

## 4. DNS и имя `wslhost` внутри WSL

Сначала сохраните управляемый WSL DNS, особенно при VPN. В дистрибутиве проверьте:

```sh
ls -l /etc/resolv.conf
cat /etc/resolv.conf
getent ahostsv4 example.com
ip -4 route
```

Адрес `192.168.100.1` — шлюз, а не автоматически работающий DNS. Если разрешение имён не работает, сначала проверьте маршруты, настройки VPN и брандмауэр. DNS-сервер должен быть достижим **из WSL** и разрешён вашей сетью; публичные `1.1.1.1` и `8.8.8.8` — лишь примеры, они могут быть заблокированы и не разрешат внутренние имена. Использование публичного DNS может раскрывать DNS-запросы и нарушать политику организации.

Ручной DNS нужен только при осознанном отказе от автоматически управляемого DNS. В `/etc/wsl.conf` добавьте `generateResolvConf=false` в существующую секцию `[network]`, не удаляя другие ключи; если секции нет, создайте её:

```ini
[network]
generateResolvConf=false
```

Это отключает генерацию `/etc/resolv.conf` в данном дистрибутиве. Для WSL DNS tunneling генерация должна оставаться включённой: ручной файл может нарушить VPN, корпоративные правила DNS и разрешение внутренних имён. После изменения сохраните работу и выполните на хосте `wsl --shutdown`, затем заново откройте дистрибутив.

Если `/etc/resolv.conf` управляется `systemd-resolved`, NetworkManager или другой службой, настройте DNS через неё и не заменяйте её ссылку. Следующий приём предназначен **только для файла или ссылки, ранее созданной WSL**, после проверки владельца и сохранения ссылки и её содержимого, как в разделе подготовки. В редакторе сначала создаётся отдельный файл; исходная запись перемещается только после сохранения непустого нового файла. Занятые имена не перезаписываются:

```sh
(
  set -eu
  saved=/etc/resolv.conf.mcpkit-before-manual-dns
  new=/etc/resolv.conf.mcpkit-manual-dns.new
  if [ -e "$saved" ] || [ -L "$saved" ] || [ -e "$new" ] || [ -L "$new" ]; then
    echo 'Одно из имён уже занято; проверьте его и остановитесь.' >&2
    exit 1
  fi
  sudoedit "$new"
  if ! sudo test -s "$new"; then
    echo 'Новый DNS-файл не сохранён; исходный не изменён.' >&2
    exit 1
  fi
  sudo chown root:root "$new"
  sudo chmod 644 "$new"
  if [ -e /etc/resolv.conf ] || [ -L /etc/resolv.conf ]; then
    sudo mv -- /etc/resolv.conf "$saved"
  fi
  if ! sudo mv -- "$new" /etc/resolv.conf; then
    echo 'Не удалось установить DNS-файл; восстановите исходную запись из копии.' >&2
    exit 1
  fi
)
```

Например, если оба публичных сервера разрешены и доступны, содержимое может быть таким; иначе подставьте DNS своей сети:

```text
nameserver 1.1.1.1
nameserver 8.8.8.8
```

Сохраните и проверьте `getent ahostsv4 example.com`, затем повторите после перезапуска дистрибутива. Если перемещение исходной записи или установка нового файла не удались, остановитесь и восстановите DNS по сохранённой копии; не размонтируйте занятый файл вслепую. Если нужен корпоративный VPN/DNS, предпочтите его настройки и восстановите автоматический режим при необходимости. Docker Desktop может использовать отдельный механизм DNS для контейнеров.

Чтобы имя `wslhost` указывало на адрес хоста из этой схемы, сначала убедитесь, что `192.168.100.1` доступен из выбранного режима WSL, а имя ещё не занято: `getent ahostsv4 wslhost` и проверка `/etc/hosts`. Затем отредактируйте `/etc/hosts` с правами администратора, сохранив все остальные строки и избегая повторного имени:

```text
192.168.100.1 wslhost
```

Проверьте `getent ahostsv4 wslhost` и повторите проверку после `wsl --shutdown`. Если WSL генерирует `/etc/hosts` заново, при необходимости можно добавить `generateHosts=false` в существующий `[network]` файла `/etc/wsl.conf`, но тогда обновления файла со стороны WSL прекращаются; при DNS tunneling этот параметр может игнорироваться. Не отключайте генерацию без учёта остальных имён и проверьте результат после перезапуска. Для NAT WSL его фактический адрес хоста может быть другим, а в `mirrored` для связи с хостом обычно достаточно `127.0.0.1`.

## 5. Подключение Windows-ВМ к `NATSwitch`

Этот раздел работает независимо от того, удалось ли подключить WSL к коммутатору. В **диспетчере Hyper-V** откройте параметры выбранной ВМ → нужный **Сетевой адаптер** → виртуальный коммутатор `NATSwitch`. Либо на хосте от администратора используйте PowerShell: подставьте реальные имена ВМ и её адаптера, сначала проверьте текущий коммутатор и MAC.

```powershell
$vmName = 'ИМЯ_ВАШЕЙ_ВМ'
Get-VMNetworkAdapter -VMName $vmName | Format-Table Name, SwitchName, MacAddress, Status
```

Выберите адаптер **по точному уникальному имени**, сохраните его прежний коммутатор для отката и только затем подключите:

```powershell
$nicName = 'ИМЯ_НУЖНОГО_АДАПТЕРА_ВМ'
$vmNic = @(Get-VMNetworkAdapter -VMName $vmName | Where-Object Name -eq $nicName)
if ($vmNic.Count -eq 1) {
    $vmNic[0] | Connect-VMNetworkAdapter -SwitchName 'NATSwitch' -ErrorAction Stop
    Get-VMNetworkAdapter -VMName $vmName | Format-Table Name, SwitchName, MacAddress, Status
} else {
    throw 'Нужен ровно один проверенный адаптер ВМ.'
}
```

Переключение существующего адаптера прервёт его прежнее соединение. При необходимости можно заранее добавить отдельный адаптер в параметрах ВМ, не трогая исходный, но тогда нужно отдельно согласовать маршруты и DNS гостя. Имя адаптера внутри Windows-ВМ может отличаться от имени в Hyper-V: сопоставьте его по MAC, не учитывая регистр и разделители в записи адреса.

## 6. Статический IPv4 и DNS в гостевой Windows

Выполняйте этот раздел **внутри Windows-ВМ**, а не на хосте. Сначала от имени администратора просмотрите и сохраните настройки, включая DHCP, DNS и маршруты:

```powershell
Get-NetAdapter | Format-Table Name, ifIndex, Status, MacAddress
Get-NetIPConfiguration -All
Get-NetIPInterface -AddressFamily IPv4 | Format-Table InterfaceAlias, InterfaceIndex, Dhcp
Get-NetRoute -AddressFamily IPv4 | Format-Table DestinationPrefix, NextHop, InterfaceAlias, RouteMetric
Get-DnsClientServerAddress -AddressFamily IPv4 | Format-Table InterfaceAlias, ServerAddresses
```

Далее приведён вариант для **выделенного адаптера**, подключённого к `NATSwitch`, без ранее настроенного IPv4 и без другого маршрута по умолчанию в ВМ. Добавление статического IPv4 через `New-NetIPAddress` отключает DHCP на выбранном интерфейсе; это может прервать соединение и изменить DNS/маршрутизацию. Если ВМ использует другую сеть, статические адреса или несколько шлюзов, сначала составьте отдельный план; не удаляйте настройки и не добавляйте второй шлюз вслепую. Для второго адаптера, если интернет должен оставаться через прежний, можно задать `.20/24` **без** нового шлюза и оставить прежний маршрут; исходящий трафик в таком случае не обязательно пойдёт через этот NAT.

Выберите один из способов — PowerShell **или** графический интерфейс.

### PowerShell в гостевой Windows

Подставьте точное имя проверенного адаптера внутри ВМ; пример `Ethernet 2` не является автоматическим выбором. Сверьте MAC с Hyper-V и ещё раз убедитесь, что на интерфейсе нет нужных существующих настроек:

```powershell
$guestNic = Get-NetAdapter -Name 'Ethernet 2' -ErrorAction Stop
$guestNic | Format-List Name, ifIndex, MacAddress, Status
Get-NetIPAddress -InterfaceIndex $guestNic.ifIndex -AddressFamily IPv4
Get-NetRoute -InterfaceIndex $guestNic.ifIndex -AddressFamily IPv4
```

Для выделенного адаптера без другого шлюза задайте адрес и шлюз:

```powershell
New-NetIPAddress -InterfaceIndex $guestNic.ifIndex -IPAddress '192.168.100.11' -PrefixLength 24 -DefaultGateway '192.168.100.1' -ErrorAction Stop
Get-NetIPAddress -InterfaceIndex $guestNic.ifIndex -AddressFamily IPv4 | Format-Table IPAddress, PrefixLength, AddressState
Get-NetRoute -InterfaceIndex $guestNic.ifIndex -AddressFamily IPv4 | Format-Table DestinationPrefix, NextHop
```

Если создание завершилось ошибкой, не продолжайте: проверьте фактический адрес и маршруты. Дождитесь состояния `Preferred` для `.20` и убедитесь, что маршрут по умолчанию ведёт через `.1`. Только затем укажите **реально доступные и разрешённые** DNS-серверы; публичные адреса ниже — пример, а не обязательное значение:

```powershell
Set-DnsClientServerAddress -InterfaceIndex $guestNic.ifIndex -ServerAddresses @('1.1.1.1', '8.8.8.8') -ErrorAction Stop
Get-NetIPConfiguration -InterfaceIndex $guestNic.ifIndex
```

Для второго адаптера с сохранением прежнего шлюза команда `New-NetIPAddress` выполняется без параметра `-DefaultGateway`; DNS выбирайте с учётом действующих правил и политики VPN.

### Через графический интерфейс гостевой Windows

Откройте список сетевых адаптеров (`ncpa.cpl`) → свойства проверенного по MAC адаптера → **IP версии 4 (TCP/IPv4)** → **Свойства**. Для выделенного адаптера выберите ручной IPv4 и задайте:

| Поле | Значение примера |
| --- | --- |
| IP-адрес | `192.168.100.11` |
| Маска подсети | `255.255.255.0` |
| Основной шлюз | `192.168.100.1` |
| Предпочитаемый и альтернативный DNS | Доступные DNS вашей сети; например, `1.1.1.1` и `8.8.8.8`, только если они разрешены. |

Сохраните настройки и проверьте результат командами диагностики. Для второго адаптера без смены текущего выхода в интернет не добавляйте новый шлюз по умолчанию без отдельного плана.

## 7. Проверки и диагностика

На хосте проверьте наличие `NATSwitch`, адреса `.1`, `MCPKit-NAT` и подключения нужной ВМ:

```powershell
Get-VMSwitch -Name 'NATSwitch' | Format-List Name, SwitchType
Get-NetNat -Name 'MCPKit-NAT' | Format-List Name, InternalIPInterfaceAddressPrefix
Get-NetIPAddress -InterfaceIndex $adapter.ifIndex -AddressFamily IPv4
Get-VMNetworkAdapter -VMName $vmName | Format-Table Name, SwitchName, MacAddress, Status
Test-NetConnection 192.168.100.11
```

Здесь `$adapter` и `$vmName` — значения, выбранные ранее на хосте; в новом сеансе задайте их заново после проверки. В гостевой Windows проверьте адрес, маршрут, шлюз и DNS, затем доступ наружу:

```powershell
Get-NetIPConfiguration -All
Get-NetRoute -AddressFamily IPv4 | Format-Table DestinationPrefix, NextHop, InterfaceAlias, RouteMetric
Test-NetConnection 192.168.100.1
Test-NetConnection 1.1.1.1
Resolve-DnsName example.com
Test-NetConnection example.com -Port 443
```

Для WSL на подтверждённом устаревшем подключении, в самом дистрибутиве:

```sh
ip -br -4 address
ip -4 route
ip route get 192.168.100.1
getent ahostsv4 wslhost
ping -c 2 192.168.100.1
ping -c 2 192.168.100.11
getent ahostsv4 example.com
curl -4 -I --connect-timeout 5 https://example.com
```

На работающей экспериментальной схеме WSL покажет `.10/24` на проверенном интерфейсе и маршрут по умолчанию через `.1`; Windows-ВМ покажет `.20/24` и шлюз `.1`. Для WSL в обычном NAT или `mirrored` ожидаются другие адреса. Если проверка IP проходит, а имя не разрешается, проверьте доступность DNS и VPN. Если внешние IP и HTTPS недоступны, проверьте выход хоста, совпадение префикса WinNAT, маршруты и правила сети. Если ВМ не видит `.1`, проверьте выбранный коммутатор, MAC и маску. После перезапуска WSL убедитесь, что запускался именно ответственный дистрибутив и его скрипт не отказал из-за изменения MAC или маршрута.

### Связь с WSL в штатном режиме

В NAT или `mirrored` проверьте выбранный WSL маршрут к Windows-ВМ командой `ip route get 192.168.100.11` и затем доступность нужного разрешённого сервиса. Наличие маршрута в Linux не доказывает, что Windows пересылает трафик между виртуальными сетями или что брандмауэры пропускают его. Соединение может требовать отдельно настроенной маршрутизации или защищённого туннеля; не включайте общую маршрутизацию и не отключайте брандмауэры вслепую.

В обратном направлении ВМ также не получает автоматически доступ к адресам WSL. Для WSL в NAT один из вариантов доступа к **отдельному TCP-сервису** — прокси порта на хосте: прослушивать только `192.168.100.1` и нужный порт, разрешить его лишь доверенной ВМ и направить на действующий адрес и порт WSL. Адрес WSL может меняться после перезапуска, а служба должна принимать подключения по выбранному адресу; в `mirrored` применяются другие правила. Это отдельная настройка, не выдающая WSL адрес `.10`: см. [варианты подключения и portproxy Microsoft](https://learn.microsoft.com/en-us/windows/wsl/networking). Не копируйте пример Microsoft с `0.0.0.0` без ограничения доступа: он слушает все IPv4-адреса хоста. Прокси не шифрует соединение; для секретов нужен проверяемый TLS или другой защищённый канал.

Ping использует ICMP, который может блокироваться Windows, гостевой системой, сетью или внешним узлом; его неудача сама по себе не доказывает отсутствие TCP-связи. Проверяйте также конкретный разрешённый TCP-сервис. Не меняйте права `ping`, не отключайте брандмауэры и не открывайте все порты ради диагностики.

Если требуется разрешить входящие ICMP-запросы на **хосте** и политика это допускает, можно создать отдельное узкое правило для проверенного адаптера, только для указанных адресов гостей. Сначала убедитесь, что правило с таким именем отсутствует и `$adapter` всё ещё указывает на нужный `vEthernet`:

```powershell
Get-NetFirewallRule -Name 'MCPKit-NAT-ICMPv4' -ErrorAction SilentlyContinue
$adapter | Format-List Name, ifIndex, MacAddress
```

Если правило отсутствует и адаптер проверен, создайте его:

```powershell
New-NetFirewallRule -Name 'MCPKit-NAT-ICMPv4' -DisplayName 'MCP Kit: ICMPv4 к NAT-шлюзу' `
  -Direction Inbound -Action Allow -Protocol ICMPv4 -IcmpType 8 `
  -InterfaceAlias $adapter.Name -LocalAddress '192.168.100.1' -RemoteAddress '192.168.100.10','192.168.100.11' -ErrorAction Stop
```

Правило не открывает TCP-порты и не настраивает брандмауэр гостевой Windows или брандмауэр Hyper-V для WSL. Для проверки в обратном направлении при необходимости создавайте столь же ограниченное правило на соответствующем госте; для приложений разрешайте только нужный TCP-порт, интерфейс и доверенный источник. Учитывайте сетевой профиль и групповые политики: они могут запрещать локальные правила. Правило `MCPKit-NAT-ICMPv4`, если создали именно его, можно отдельно удалить через `Remove-NetFirewallRule -Name 'MCPKit-NAT-ICMPv4'`. См. [брандмауэр Hyper-V для WSL](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/hyper-v-firewall).

## 8. Что это меняет для MCP Kit

- Linux GLOBAL и Windows LOCAL управляют **разными** экземплярами MetaMCP, своими настройками и ключами. Сеть и `wslhost` сами по себе не регистрируют Windows-серверы в Linux; стандартная Windows-установка работает со своим локальным MetaMCP.
- Windows-шлюз по умолчанию слушает `127.0.0.1:13001`, а интерфейс и серверная часть Windows MetaMCP — `127.0.0.1:13008`/`13009`. Адрес `.1` или `.20` и маршрут к ним не делают эти loopback-порты автоматически доступными другой ВМ. Особый localhost-механизм `mirrored` относится к взаимодействию WSL с хостом и не делает `127.0.0.1` общей для обычной Windows-ВМ. Linux-порты и привязки Docker проверяйте отдельно.
- Для удалённого доступа нужны явно спроектированные прослушиваемый адрес/туннель, маршруты, узкие правила брандмауэра и проверяемый TLS либо другой защищённый канал. Не меняйте шлюз на `0.0.0.0` только ради прохождения проверки: автоматическая локальная Docker-регистрация Windows требует IPv4 loopback и HTTP без TLS; другая привязка или TLS могут нарушить её работу.
- [Низкоуровневый регистратор](configuration.md#linux-низкоуровневая-регистрация-windows-шлюза) — отдельный механизм: Windows-скрипт не создаёт для него готовый JSON и не настраивает защищённую связь. Адрес шлюза должен быть доступен из контейнера приложения Linux MetaMCP. Ключи и регистрационный JSON передавайте только по защищённому каналу; `allowInsecureLan` в настройках шлюза или регистрационном JSON **не шифрует** трафик и не заменяет TLS/VPN/туннель. Один ключ шлюза даёт доступ ко всем его серверам, включая управление файлами и рабочим столом.

## 9. Откат

1. Сохраните текущую работу. Остановите экспериментальный автозапуск WSL, восстановив прежний `/etc/wsl.conf` или удалив **только добавленную** строку `command`; не теряйте изменения, сделанные после резервного копирования. Восстановите прежние `.wslconfig`, `/etc/hosts` и DNS-конфигурацию/символическую ссылку из проверенных копий, учитывая владельца DNS. Если файла изначально не было, удаляйте только созданный вами файл после проверки. Сохранённый `resolv.conf.content` — копия данных, а не замена настройке исходной службы. При необходимости удалите только созданный вами `/usr/local/sbin/mcpkit-wsl-network` после отключения его запуска.
2. Для ещё работающего WSL заново определите и задайте `nic` в текущей оболочке, если это новый сеанс; проверьте его имя, MAC и записи через `ip -4 address show dev "$nic"` и `ip -4 route`. **Только если эти записи были добавлены вами и не используются другим менеджером**, удалите их с проверенного интерфейса: `sudo ip route del default via 192.168.100.1 dev "$nic"` и `sudo ip address del 192.168.100.10/24 dev "$nic"`. Удаляйте только существующие записи; не очищайте все адреса. Если вручную поднимали ранее выключенный интерфейс, восстановите его состояние по сохранённой конфигурации. Затем выполните на хосте `wsl --shutdown` и откройте нужный дистрибутив; это остановит все WSL-дистрибутивы.
3. В Windows-ВМ восстановите прежний коммутатор её проверенного адаптера через Hyper-V и сохранённые IPv4, шлюз и DNS. Если раньше на этом адаптере использовался DHCP, после удаления **только созданных в примере** адреса `.20` и маршрута через `.1` можно вернуть DHCP и автоматический DNS через свойства IPv4; если настройки были статическими, восстановите именно сохранённые значения. Не сбрасывайте все сетевые интерфейсы ВМ.
4. Только когда убедились, что коммутатор и NAT были созданы вами и больше никому не нужны, отсоедините от них ВМ, остановите использовавшие их дистрибутивы и удалите отдельно созданное правило брандмауэра. В PowerShell хоста заново задайте `$adapter`, если это новый сеанс, и ещё раз проверьте имя, MAC и индекс. Затем удалите только созданные объекты: `Remove-NetNat -Name 'MCPKit-NAT'`, `Remove-NetIPAddress -InterfaceIndex $adapter.ifIndex -IPAddress '192.168.100.1'` и `Remove-VMSwitch -Name 'NATSwitch'`. Не используйте команды массового удаления. Удаление NAT прерывает соединения использующих его гостей; если объект оказался общим или его происхождение неясно, остановитесь и разберите зависимости.
5. Проверьте прежние `Get-NetNat`, `Get-VMSwitch`, маршруты, DNS и работу Docker/WSL/ВМ. Если за время эксперимента настройки менялись другими средствами, не перезаписывайте их старой копией без сверки.
